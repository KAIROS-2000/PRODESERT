# Контракт интеграции Pro Dessert с 1С

Статус: обязательный контракт для mock-, CommerceML 2- и REST-адаптеров. Конкретная конфигурация 1С и её доработки должны быть подтверждены владельцем магазина до production-подключения.

## 1. Область и инварианты

1С — источник истины для UUID номенклатуры, артикулов, базовых названий и вариантов, характеристик, единиц измерения, ставок НДС, цен, остатков, резервов, факта оплаты, возвратов и исполнимых статусов заказа. Сайт владеет SEO, slug, расширенными описаниями, web-изображениями и alt-текстами, рекомендациями, синонимами, баннерами и информационными страницами. Импорт не вправе перезаписывать поля владельца сайта.

Обязательные инварианты обмена:

- `fulfillmentMethod` всегда равен `PICKUP`;
- `paymentMethod` всегда равен `BANK_TRANSFER`;
- единственная точка первой версии — магазин Pro Dessert, Оренбург, Липовая улица, 20; её технический идентификатор согласуется отдельно;
- адрес покупателя, стоимость перевозки, курьер, транспортная компания и отгрузочные сущности не передаются и не принимаются;
- реквизиты на оплату разрешено отправить клиенту только после подтверждения наличия и создания резерва;
- загруженное клиентом подтверждение не устанавливает `PAID`; оплату подтверждает менеджер, 1С либо согласованная будущая сверка банковской выписки;
- один UUID 1С однозначно соответствует одной нормализованной сущности товара или варианта;
- повтор сообщения не создаёт второй заказ, платёж, резерв или переход статуса;
- неизвестный UUID, расхождение суммы и недопустимый переход статуса не исправляются молча;
- категории 1С проходят слой нормализации и не превращаются напрямую в публичные URL;
- точные остатки не раскрываются публично без отдельного решения владельца.

## 2. Нормализованный adapter interface

Бизнес-логика использует только этот интерфейс. Форматы конкретной 1С изолированы внутри адаптера.

```ts
export type OneCAdapterKind = 'mock' | 'commerceml2' | 'rest';

export interface ExchangeCursor {
  value: string | null;
}

export interface ImportPage<T> {
  items: readonly T[];
  nextCursor: string | null;
  sourceRevision: string;
}

export interface ExportReceipt {
  externalOrderId: string;
  acceptedAt: string;
  sourceRevision: string | null;
}

export interface OneCAdapter {
  readonly kind: OneCAdapterKind;
  health(signal?: AbortSignal): Promise<AdapterHealth>;
  pullCatalog(cursor: ExchangeCursor, signal?: AbortSignal): Promise<ImportPage<CatalogItem>>;
  pullPrices(cursor: ExchangeCursor, signal?: AbortSignal): Promise<ImportPage<PriceItem>>;
  pullInventory(cursor: ExchangeCursor, signal?: AbortSignal): Promise<ImportPage<InventoryItem>>;
  pullOrderEvents(cursor: ExchangeCursor, signal?: AbortSignal): Promise<ImportPage<OrderEvent>>;
  pushOrder(command: ExportOrderCommand, signal?: AbortSignal): Promise<ExportReceipt>;
}
```

Все реализации обязаны проходить один набор contract tests. В production допустимы только `commerceml2` и `rest`; запуск production с `mock` завершается ошибкой конфигурации.

### CommerceML 2

- Адаптер принимает только согласованную с владельцем версию и профиль CommerceML; универсальная совместимость не предполагается.
- XML разбирается потоково; DTD и внешние сущности отключены, установлены лимиты размера файла, глубины XML, числа элементов и времени обработки.
- Каталог, предложения, цены и остатки преобразуются в нормализованные DTO ниже.
- Исходный файл получает SHA-256, `messageId`, журнал обработки и безопасный срок хранения; секреты и открытые персональные данные в журнал не попадают.
- Частичный или повторный файл не считается новым обменом только из-за нового имени файла.
- Выгрузка заказа формируется по согласованной схеме CommerceML либо через отдельный REST-командный endpoint, если конфигурация 1С не поддерживает требуемые поля заказа.

### REST

- JSON, UTF-8, HTTPS, `Content-Type: application/json`.
- Контракт версионируется URL `/api/v1/integration/1c` и полем `schemaVersion`.
- Пакетный endpoint возвращает результат каждого элемента, а не только общий HTTP-статус.
- Размер пакета и лимит запросов задаются конфигурацией после нагрузочного теста.

## 3. Общий envelope и правила типов

```json
{
  "schemaVersion": "1.0",
  "messageId": "0190f3ad-f42e-7b74-8a54-a78f0d6a0c8e",
  "eventType": "inventory.updated",
  "occurredAt": "2026-07-18T06:30:00Z",
  "source": "ONE_C",
  "correlationId": "0190f3ad-f47a-7e0c-8505-3daf412e71ff",
  "idempotencyKey": "one-c:inventory:warehouse-1:revision-4815",
  "sourceRevision": "4815",
  "payload": {}
}
```

- Время — RFC 3339 в UTC; исходный часовой пояс 1С фиксируется в настройках.
- Деньги и количества — десятичные строки, без binary float; валюта первой версии — `RUB`.
- Внешние идентификаторы — непустые строки; UUID 1С сохраняется без преобразования регистра или формата.
- `null` означает явное очищение только для nullable-поля. Отсутствующее поле не изменяет сохранённое значение.
- `sourceRevision` монотонен в пределах потока и используется для защиты от запоздавших событий.
- Полный импорт помечается явно; отсутствие позиции в инкрементальном пакете не деактивирует её.

Успешный ответ:

```json
{
  "messageId": "0190f3ad-f42e-7b74-8a54-a78f0d6a0c8e",
  "correlationId": "0190f3ad-f47a-7e0c-8505-3daf412e71ff",
  "status": "ACCEPTED",
  "receivedAt": "2026-07-18T06:30:01Z",
  "results": [{ "externalId": "a1473c1f-1e3f-11ef-9a8d-00155d010101", "status": "APPLIED" }]
}
```

`ACCEPTED` означает приём в надёжную очередь, но не обязательно завершение бизнес-обработки. Итог доступен в журнале по `messageId` и `correlationId`.

## 4. Входящие потоки: 1С → сайт

### 4.1 Каталог

`POST /api/v1/integration/1c/catalog/import`

```json
{
  "externalProductId": "a1473c1f-1e3f-11ef-9a8d-00155d010101",
  "externalVariantId": "a1473c20-1e3f-11ef-9a8d-00155d010101",
  "sku": "PD-000184",
  "baseName": "Шоколад тёмный",
  "variantName": "54,5%, 1 кг",
  "brandExternalId": "brand-callebaut",
  "brandName": "Callebaut",
  "sourceCategoryIds": ["one-c-category-17"],
  "active": true,
  "unit": { "code": "PCE", "name": "шт." },
  "vatRate": "20.00",
  "minimumQuantity": "1",
  "quantityStep": "1",
  "attributes": [
    { "code": "COCOA_PERCENT", "name": "Содержание какао", "value": "54.5", "unit": "%" }
  ],
  "sourceImages": [
    {
      "externalId": "image-184-1",
      "url": "https://1c.example.invalid/image/184",
      "sha256": "<sha256>"
    }
  ]
}
```

`sourceImages` — входные кандидаты. Они не удаляют вручную отобранные web-изображения и не меняют alt-тексты. Импорт проверяет MIME, размер, доступность и хеш.

Обязательные проверки: уникальность UUID и артикула по согласованным правилам, существование бренда или допустимость его создания, типы характеристик, единица измерения, НДС, минимум и кратность. Неизвестная категория попадает в очередь сопоставления, а не создаёт случайный публичный раздел.

### 4.2 Цены

`POST /api/v1/integration/1c/prices/import`

```json
{
  "externalVariantId": "a1473c20-1e3f-11ef-9a8d-00155d010101",
  "priceTypeExternalId": "retail",
  "amount": "1750.00",
  "oldAmount": "1890.00",
  "currency": "RUB",
  "validFrom": "2026-07-18T06:25:00Z",
  "sourceRevision": "4816"
}
```

Цена не редактируется сайтом. Отрицательные значения, неизвестная валюта, `oldAmount < amount` и устаревшая ревизия отклоняются либо помещаются на разбор согласно согласованному правилу. Изменение цены инвалидирует каталог и приводит к повторной серверной проверке корзины.

### 4.3 Остатки

`POST /api/v1/integration/1c/inventory/import`

```json
{
  "externalVariantId": "a1473c20-1e3f-11ef-9a8d-00155d010101",
  "warehouseExternalId": "orenburg-lipovaya-20",
  "onHand": "12",
  "reserved": "3",
  "available": "9",
  "pickupAvailable": true,
  "measuredAt": "2026-07-18T06:29:30Z",
  "sourceRevision": "4817"
}
```

Согласованная формула `available` фиксируется до запуска. Если 1С передаёт только компоненты, сайт вычисляет доступное количество строго по утверждённой формуле. Отрицательное доступное количество, неизвестный склад, нарушение `available <= onHand` или запоздавшая ревизия создают расхождение и не публикуются молча.

### 4.4 Статус, состав, сумма, резерв и оплата заказа

`POST /api/v1/integration/1c/orders/status`

```json
{
  "externalOrderId": "1c-order-00009142",
  "publicNumber": "PD-2026-00009142",
  "eventId": "1c-order-00009142:event:27",
  "orderVersion": 7,
  "status": "AWAITING_PAYMENT",
  "confirmedTotal": "3500.00",
  "currency": "RUB",
  "reservation": {
    "externalReservationId": "reserve-009142",
    "status": "ACTIVE",
    "expiresAt": "2026-07-19T06:30:00Z"
  },
  "payment": {
    "status": "NOT_PAID",
    "confirmedAt": null,
    "externalPaymentId": null
  },
  "lines": [
    {
      "externalVariantId": "a1473c20-1e3f-11ef-9a8d-00155d010101",
      "quantity": "2",
      "confirmedUnitPrice": "1750.00",
      "confirmedLineTotal": "3500.00"
    }
  ],
  "comment": "Наличие подтверждено"
}
```

Допустимые статусы:

`DRAFT`, `CREATED`, `AWAITING_STOCK_CONFIRMATION`, `AWAITING_PAYMENT`, `PAYMENT_VERIFICATION`, `PAID`, `ASSEMBLING`, `READY_FOR_PICKUP`, `COMPLETED`, `CANCELLED_BY_CUSTOMER`, `CANCELLED_BY_STORE`, `RESERVATION_EXPIRED`, `RETURN_REQUESTED`, `RETURNED`.

Каждый переход проходит state machine. История неизменно сохраняет старый и новый статус, дату и время, инициатора, источник `ONE_C`, комментарий, `correlationId`, `eventId`, версию и безопасные технические метаданные. Пропуск версии, регресс версии и недопустимый переход отклоняются. Расхождение состава или суммы блокирует отправку реквизитов и создаёт задачу менеджеру.

`payment.status = CONFIRMED` может инициировать `PAID` только после проверки полномочий источника и допустимости перехода. `reservation.status = EXPIRED` освобождает локальную проекцию резерва идемпотентно; заказ сохраняется.

## 5. Исходящий поток: сайт → 1С

## 6. Версионирование и совместимость

- Breaking change повышает major URL и `schemaVersion`; старая major-версия поддерживается в течение согласованного окна миграции.
- Добавление необязательного поля — minor change; consumer игнорирует неизвестные поля, но не неизвестные enum-значения.
- Удаление поля, изменение типа, смысла денег, формулы остатка или enum — breaking change.
- JSON Schema/OpenAPI и фикстуры версионируются вместе с кодом; consumer-driven contract tests обязательны до выкладки.
- В сообщении сохраняется версия, с которой оно было принято. Replay использует исходную версию и тот же ключ.

## 7. Идемпотентность, порядок и конкурентность

- Входящие сообщения имеют уникальность `(source, eventType, idempotencyKey)` и хеш канонического payload.
- Повтор с тем же ключом и хешем возвращает сохранённый результат. Тот же ключ с другим payload даёт `IDEMPOTENCY_CONFLICT`.
- `eventId` уникален для события заказа; `orderVersion` защищает от перестановки событий.
- Импорт цены и остатка применяет compare-and-set по `sourceRevision` в транзакции.
- Создание и продление резерва используют блокировку строки либо эквивалентный атомарный механизм. Повтор не увеличивает резерв.
- Outbox создаётся в одной транзакции с заказом или изменением состояния; отправка не выполняется напрямую из HTTP-транзакции.
- Inbound inbox сохраняет статус `RECEIVED`, `PROCESSING`, `APPLIED`, `REJECTED` или `DLQ`.

## 8. Защита канала

Минимум для production — HTTPS и HMAC; предпочтительно дополнительно mTLS и IP allowlist.

REST-заголовки:

- `X-PD-Key-Id`;
- `X-PD-Timestamp` — Unix seconds;
- `X-PD-Nonce` — уникальное случайное значение;
- `X-PD-Content-SHA256`;
- `X-PD-Signature`;
- `X-Correlation-Id`;
- `Idempotency-Key`.

Каноническая строка HMAC-SHA256:

```text
HTTP_METHOD\n
PATH_AND_QUERY\n
X_PD_TIMESTAMP\n
X_PD_NONCE\n
X_PD_CONTENT_SHA256
```

Сервер сравнивает подпись constant-time, допускает отклонение часов не более настроенного окна (рекомендуемо 300 секунд) и хранит использованные nonce в Redis дольше этого окна. Ключи имеют `keyId`, период ротации и перекрывающее окно. Секреты находятся только в secret storage, не в БД, логах или репозитории.

mTLS проверяет цепочку, SAN и срок сертификата. IP allowlist — дополнительный контроль, а не замена подписи. Интеграционные endpoints имеют отдельную аутентификацию, rate limit, лимит тела и аудит. Логи маскируют телефон, email, реквизиты и содержимое документов.

## 9. Outbox, retry, DLQ, журнал и replay

Повторяются только timeout, сетевые ошибки, `429` и `5xx`. Ошибки авторизации, схемы, бизнес-валидации и конфликт ключа автоматически не повторяются.

Рекомендуемый профиль с full jitter: немедленно, 5 секунд, 30 секунд, 2 минуты, 10 минут, 30 минут; затем DLQ. Параметры конфигурируются, число попыток ограничено. `Retry-After` учитывается.

Журнал обмена хранит:

- направление, адаптер и тип события;
- `messageId`, `idempotencyKey`, `correlationId`, внешний и внутренний ID;
- версию схемы и source revision;
- время приёма, начала, окончания, следующей попытки;
- число попыток, безопасный код ошибки, HTTP-статус;
- хеш payload и ссылку на защищённое исходное сообщение;
- итог обработки и инициатора ручного действия.

Replay доступен только ADMIN, требует причины, попадает в audit log и сохраняет исходные идентификаторы. Перед replay исправляется причина ошибки. Запрещено редактировать payload внутри DLQ; корректировка создаёт новое компенсирующее сообщение с новым `messageId`, но явной ссылкой на исходное.

## 10. Согласованность и reconciliation

- Цена и остаток обновляются каждые 1–5 минут; заказ экспортируется немедленно; статус поступает событием либо коротким polling; полный контрольный обмен выполняется ночью.
- Конкретные интервалы, допустимая давность данных и SLA утверждаются с владельцем 1С.
- Перед добавлением, изменением количества, открытием корзины, созданием заказа и подтверждением менеджером выполняется проверка доступности.
- При недоступности 1С заказ может оставаться в `AWAITING_STOCK_CONFIRMATION`, но реквизиты не выдаются и резерв не считается созданным.
- Ночной reconciliation сопоставляет UUID, активность, цены, остатки по складам, резервы, суммы, состав, статус и факт оплаты.
- Расхождения классифицируются, отображаются ADMIN и не затираются последующим успехом без записи решения.
- `TOTAL_MISMATCH`, неизвестный UUID, двойной резерв, неизвестный склад и дубль заказа требуют алерта.
- После полного импорта проверяются контрольные количества и хеши партий. Массовая деактивация или резкое изменение остатков требует защитного порога и ручного подтверждения.
- Очереди измеряются по lag, age oldest message, retries и DLQ size. Health endpoint различает `healthy`, `degraded` и `unavailable`.

## 12. Mock и production boundary

Mock реализует тот же `OneCAdapter`, схемы, подпись (в integration tests), идемпотентность, порядок версий и error contract. Он использует явно демонстрационные UUID и данные и поддерживает сценарии:

- успешный полный и инкрементальный импорт;
- изменение цены во время checkout;
- уменьшение и отсутствие остатка;
- повтор сообщения и конфликт idempotency key;
- timeout, `429`, `5xx`, retry и DLQ;
- неизвестный UUID и устаревшую ревизию;
- подтверждение наличия, резерв, истечение резерва;
- расхождение суммы;
- подтверждение оплаты и полный путь до `READY_FOR_PICKUP`/`COMPLETED`.

Mock не доказывает совместимость с реальной конфигурацией. Production credentials никогда не используются в mock. Конфигурация задаётся явным `ONE_C_ADAPTER=mock|commerceml2|rest`; скрытого fallback на mock нет.

## 13. Данные, необходимые от владельца реальной 1С

До production-подключения должны быть получены и письменно подтверждены:

- название конфигурации, версия платформы, режим совместимости и список доработок;
- CommerceML-профиль/версия либо OpenAPI/JSON Schema REST и тестовый контур;
- примеры полного и инкрементального обмена, включая ошибки и повтор;
- кодировка, часовой пояс, точность денег и количеств;
- объём каталога, частота изменений, пиковые размеры пакетов и лимиты;
- UUID товаров и вариантов, правила уникальности артикула, дубли и архивные позиции;
- модель характеристик, фасовок, серий, сроков годности, единиц и кратности;
- источник брендов, категорий и правила их нормализации на сайте;
- виды цен, валюта, старая цена, акции, НДС и правила округления;
- склады, склад самовывоза, формула `available`, отрицательные остатки и товары под заказ;
- источник и формат изображений, права доступа и правила обновления;
- правила резервирования, момент создания, TTL, продление, освобождение и конкурентность;
- формат заказа, присвоение ID/номера в 1С и правила изменения состава или суммы;
- точная таблица переходов статусов, источники истины, отмены, получение и возвраты;
- процесс банковского перевода, источник факта оплаты и уполномоченный подтверждать `PAID`;
- реквизиты юридического лица и шаблон PDF-счёта — отдельно от технических секретов;
- endpoint/каталог обмена, DNS, сертификаты, HMAC keys, IP allowlist и ротация;
- существующие обмены, фоновые задания, регламентные окна и возможные блокировки;
- SLA, допустимая давность цены/остатка, окно обслуживания и контакты ответственных;
- требования к журналированию, срокам хранения, персональным данным и резервным копиям;
- правила reconciliation, допустимые расхождения и процедура ручного исправления;
- критерии приёмки, тестовые заказы и согласованное окно end-to-end испытаний.

До получения этих данных production-адаптер имеет статус `BLOCKED_BY_EXTERNAL_DATA`. Разрешён mock для разработки и staging с явной маркировкой; утверждать готовность реальной интеграции нельзя.

## 14. Приёмка контракта

Интеграция принимается только при наличии следующих доказательств:

1. Contract tests одинаково проходят для mock и выбранного production-адаптера.
2. Повтор каждого входящего и исходящего сообщения не создаёт дубль; конфликт payload обнаруживается.
3. 100 последовательных тестовых заказов экспортируются без потерь и двойных заказов.
4. Цена и остаток сходятся с контрольной выборкой 1С; устаревшие события не откатывают данные.
5. Неизвестный UUID, расхождение суммы и недопустимый статус видны в журнале и ADMIN.
6. Retry применяется только к временным ошибкам; исчерпание попыток ведёт в DLQ; replay аудируется.
7. HMAC, mTLS при включении, nonce, clock skew, ротация ключа и IP allowlist проверены негативными тестами.
8. PII и секреты отсутствуют в структурированных логах, error responses и tracing.
9. Резерв создаётся один раз, влияет на доступное количество, истекает и освобождается идемпотентно.
10. Реквизиты не доступны до подтверждения наличия и активного резерва; документ клиента не подтверждает оплату автоматически.
11. Все экспортированные заказы содержат только `PICKUP` и `BANK_TRANSFER`; запрещённых полей нет в DTO, OpenAPI, БД интеграции и фикстурах.
12. Ночной reconciliation и алерты подтверждены искусственно внесёнными расхождениями.
13. Отказ 1С переводит интеграцию в `degraded`/`unavailable`, не теряет outbox и не вводит клиента в заблуждение.
14. Владельцы бизнеса и 1С подписали mapping UUID, складов, цен, статусов, резервов и оплаты.
